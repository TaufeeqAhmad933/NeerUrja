# NeerUrja (नीर ऊर्जा) — run the building when the sun is up

Solar-aware water-pump scheduling. A facility manager enters rooftop-solar capacity, the
electrical limit, tank details, pump specifications and a daily routine. NeerUrja compares three
strategies on the same simulated day:

1. **habit** - the existing fixed pump schedule,
2. **timer** - a fixed midday window with tank safeguards,
3. **optimizer** - a forecast-aware, constraint-respecting schedule.

The optimizer plans with **forecast** solar and **forecast** water demand. All three schedules
are then evaluated against a separate **actual** profile (clear day and cloudy day), so the
optimizer never has perfect knowledge of the future, and any shortage caused by forecast error is
reported, not hidden.

This package contains the **backend, infrastructure, data and docs**. The React frontend lives in
`frontend/` and is maintained separately.

```
neerurja/
├── backend/        FastAPI + Mangum app, simulator, strategies, optimizer, tests
├── infra/          AWS SAM template (template.yaml)
├── data/           demo_scenario.json  (SIMULATED demo scenarios)
├── docs/           API_CONTRACT.md  and  api-types.ts (reference TypeScript types)
├── scripts/        generate_demo_data.py
└── frontend/       (not part of this package)
```

## What is simulated, and what is not validated

* **Every input profile is synthetic**: solar, water demand, building load, tariff and the
  "existing habit" pump schedule are generated by `scripts/generate_demo_data.py`. They are not
  measurements and the forecasts are not validated forecasts.
* Results show what the **model** computes for those assumptions. They are **not evidence of
  real-world savings**. Real-world benefit is unvalidated until the model is run on measured data
  from an actual building.
* Cost = grid import x tariff minus export revenue. Demand charges, fixed charges, taxes and
  emissions are not modelled, and no emissions claims are made.
* The system does **not** control physical pumps and does not trade electricity.
* The optimizer is exact only under conditions described in `backend/README.md`; otherwise it is
  near-optimal. Feasibility is guaranteed under the forecast only.
* The saving depends heavily on the export policy. With `compensated_export` at the import tariff
  (1:1 net metering) shifting the pump saves essentially nothing, and the API says so.

## Setup (Python 3.12)

From the repository root.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend/requirements-dev.txt
```

macOS / Linux:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements-dev.txt
```

`requirements.txt` holds only what the Lambda needs (so `sam build` stays small).
`requirements-dev.txt` adds pytest, httpx, uvicorn (local server) and boto3 for local work.

## Run the API locally

```bash
uvicorn app.main:app --reload --app-dir backend
```

* Health: <http://127.0.0.1:8000/health>
* Interactive docs: <http://127.0.0.1:8000/docs>
* Demo scenario: <http://127.0.0.1:8000/api/v1/scenarios/demo?weather=cloudy>

No AWS account or credentials are needed locally. The frontend uses
`VITE_API_BASE_URL=http://127.0.0.1:8000`; local CORS already allows `http://localhost:5173` and
`http://127.0.0.1:5173`.

## Run the tests

```bash
cd backend
python -m pytest -q
```

## Generate / load the demo scenarios

```bash
python scripts/generate_demo_data.py            # (re)write data/demo_scenario.json
python scripts/generate_demo_data.py --check    # verify the committed file is up to date
```

`data/demo_scenario.json` holds a `clear` and a `cloudy` scenario, each a ready-to-POST request.
The API loads them from S3 when `DEMO_BUCKET` is set, otherwise from the local file, otherwise
generates the same scenarios in memory.

## Configuration (environment variables)

| Variable | Default | Meaning |
|---|---|---|
| `DEMO_BUCKET` | unset | If set, demo scenarios are read from this S3 bucket. S3 errors return HTTP 503; there is no silent fallback. |
| `DEMO_OBJECT_KEY` | `scenarios/demo_scenario.json` | S3 key of the scenario file |
| `DEMO_SCENARIO_PATH` | unset | Local scenario file override (local development only) |
| `FRONTEND_ORIGIN` | `http://localhost:5173,http://127.0.0.1:5173` | Allowed CORS origin(s), comma-separated, no trailing slash |
| `POWERTOOLS_SERVICE_NAME` | `neerurja-api` | Service name in structured logs |
| `POWERTOOLS_LOG_LEVEL` | `INFO` | Log level |

CORS is handled in one place, the FastAPI middleware, so it behaves the same locally and behind
API Gateway. In AWS it is set by the `FrontendOrigin` stack parameter.

## AWS: what is genuinely used

Defined in `infra/template.yaml` and exercised by the code:

| Service / tool | Real purpose |
|---|---|
| AWS Lambda (Python 3.12) | Runs the simulation, optimizer and metrics (`app.main.handler`) |
| Amazon API Gateway (HTTP API) | HTTPS front door, with throttling (burst 20, 10 req/s) |
| Amazon S3 | Private, encrypted bucket holding the demo scenario file read by the Lambda |
| Amazon CloudWatch Logs | Function log group (14-day retention) receiving structured logs |
| AWS SAM CLI (open source) | Builds and deploys the stack |
| AWS Lambda Powertools for Python (open source) | Structured JSON logger used in the handler and the endpoints |
| IAM | Function role limited to `s3:GetObject` on the single demo object, plus basic logging |

**Amplify Hosting** is for the frontend and is **not** defined in this package; it is set up
separately from the GitHub repository. There is no database, no VPC/NAT gateway, no EC2 and no
always-on compute.

## Build and deploy with SAM

Prerequisites: an AWS account, AWS CLI configured **locally** (`aws configure`; never paste keys
into any chat or commit them), SAM CLI installed (`sam --version`), Python 3.12.

1. **Set a budget alert first** (AWS Billing console -> Budgets). A budget alert is a
   notification, not a spending cap. Check actual charges while testing.
2. Run the tests (above).
3. Build and deploy from the repository root:

   ```bash
   sam build --template-file infra/template.yaml
   sam deploy --guided
   ```

   `--guided` asks for a stack name (for example `neerurja`), a region, and the parameters. Accept
   the default `FrontendOrigin` for now. If the build complains about native wheels (Windows),
   use `sam build --template-file infra/template.yaml --use-container` (needs Docker).
4. Note the stack outputs `ApiUrl` and `DemoBucketName`
   (`aws cloudformation describe-stacks --stack-name neerurja --query "Stacks[0].Outputs"`).
5. **Upload the demo scenario** (the bucket is created empty):

   ```bash
   aws s3 cp data/demo_scenario.json s3://<DemoBucketName>/scenarios/demo_scenario.json
   ```

6. Test the deployed API:

   ```bash
   curl <ApiUrl>/health
   curl "<ApiUrl>/api/v1/scenarios/demo?weather=clear"
   ```

   A 503 from the demo endpoint means the S3 object is missing or unreadable.
7. Set `VITE_API_BASE_URL=<ApiUrl>` (no trailing slash) in the Amplify build environment.
8. Once Amplify gives you a URL, allow it for CORS and redeploy:

   ```bash
   sam deploy --parameter-overrides FrontendOrigin=https://main.xxxxxxxx.amplifyapp.com
   ```

9. Inspect logs: CloudWatch -> Log groups -> `/aws/lambda/<stack-name>-api` (JSON entries such
   as `scenario_run` with elapsed time and costs).

## Remove everything when finished

```bash
aws s3 rm s3://<DemoBucketName> --recursive     # CloudFormation cannot delete a non-empty bucket
sam delete --stack-name neerurja
```

Then confirm in the console that the stack, bucket, API and log group are gone. Remove the Amplify
app separately.
